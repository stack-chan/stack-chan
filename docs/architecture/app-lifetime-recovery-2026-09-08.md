# 遅延した終了処理と会話失敗からの復旧 — 2026-09-08

残件3・5の境界で、次の不具合を再現して修正した。

- AppSession終了後にsetupが非同期disposerを返すと、そのrejectを観測していなかった。完了を観測して既存のエラー通知へ渡し、二重実行やアプリの再開を防ぐ。通常の同期disposerも維持する。SDKは `AppDisposer` として同期・非同期の終了処理を明示する。
- 接続のイベント購読も、非同期handlerのrejectを報告する。最初のawaitまでの通知順序は同期のまま保ち、接続終了で購読を解除して後続通知を止める。任意のJavaScript Promiseを強制停止したり、終了を無期限に待たせたりはしない。
- SDK対話は道具の往復中に保存用の応答IDを更新していたため、後続の通信失敗で不完全な履歴を次の要求へ持ち越した。往復中のIDと成功した会話のIDを分け、askの正常完了時だけ確定する。通信失敗・取消・往復上限・応答長超過では最後に成功した履歴を維持する。

変更前のテストで、遅延disposerの失敗が未報告になることと、失敗後に未確定の応答IDが送信されることを確認した。変更後はNode 564件、厳密なSDK型検査、architecture 77件、XS全58 manifest（69.8秒）が成功した。遅延disposerは100回の置換、接続はイベント通知と購読の両方、対話は上記4種類の失敗とその後の成功を検証した。

M5StackとM5StackChan CoreS3のreleaseを再ビルドし、容量・版・機種の検査が成功した。本体はそれぞれ3,795,536 / 6,580,176 bytes。最新WASMとWebを使ったChromium検証で、Galleryの4 archiveと生成した顔・入力・音声の動作、置換時の待機・周期処理の終了も確認した。

SDKの周期処理の説明も現行実装に揃えた。handlerの失敗を報告し、次の周期に再試行する。実サービスへ会話の要求は送っておらず、この検証はホスト側の所有・取消・履歴管理を対象とする。

無線の競合と物理的な停止完了、provider参照ライブラリー、音声の残る置換経路を引き続き確認する。実機・電源断・初学者受入と製品ソースの純減は未完了である。
