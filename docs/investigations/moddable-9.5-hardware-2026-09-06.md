# SDK 9.5のM5StackChan CoreS3実機検証

## 検証環境

PR #692の`bf5153f5`をM5StackChan CoreS3（ESP32-S3、16 MiBフラッシュ）で検証した記録です。
Web Radio専用アプリの検証には、後述する起動依存の修正`795006e3`を含みます。
未改変のModdable SDK 9.5.0とESP-IDF 6.1を使用し、通常のホストはデバッグ版で動かしています。
既存の作業ツリーとSDKを変更せず、専用の作業ツリーでビルドしました。
書き込み前にシリアルポートの利用者を確認し、現在のフラッシュ全体をバックアップしました。
バックアップには設定が含まれるため、リポジトリには保存していません。

## 専用アプリの電源初期化

Web Radio専用アプリは、起動時に`axp2101-power-capture`を見つけられず停止しました。
基板の`setup-target.js`はこのモジュールを使用しますが、宣言とpreloadは通常ホストの電源サービスに依存していました。
`795006e3`では基板のmanifestにもモジュールとpreloadを宣言し、通常ホストを含まないアプリでも電源初期化を実行できるようにしました。
修正後の専用アプリでWi-Fi接続と再生開始を確認し、通常ホストのリリースビルド、78件のアーキテクチャ検査、manifestの静的検査も成功しています。

## HTTPテストのメモリ条件

Linux向けの既存テストをMODに移して実行すると、73,728バイトの応答を受信するテスト用クライアントの文字列連結で`XS abort: memory full`になりました。
停止位置は受信コールバックの`received += String.fromArrayBuffer(this.read(count))`です。
この構成では、同じXSマシンにホストUI、HTTPサーバーの応答、クライアントの受信文字列が共存します。

実機内の往復テストでは応答を9,216バイトにして全項目を実行しました。
73,728バイトの応答はPC側のクライアントで受信し、内容の一致と継続要求の成功を確認しました。
製品コードのヒープ設定や応答処理は変更していません。
任意のサイズの応答を送れることや、複数の大きな応答を並列処理できることを示す試験ではありません。

## HTTPSの証明書条件

`example.com`へのHTTPS接続では`Resource not found: ca67.der`によってTLS処理が停止しました。
ホストが同梱するCAは限定されており、この接続が必要としたCAは含まれていません。
`ca67`、`ca109`、`ca176`、`ca233`、`ca236`をSDK 9.0と9.5で比較すると、それぞれのDERファイルは同一でした。
この結果をSDK更新による証明書の番号変更とは扱っていません。
任意のHTTPS接続先を利用するMODでは、その接続先に必要なCAの同梱と実接続による確認が必要です。

## 音声試験の方法

ChatAudioIOには製品の`StackChanChatAudioIO`と`xiaozhiV1`ワーカーを使用します。
PC上の試験サーバーは受信したマイク音声を保存せず、パケット数とバイト数を数えます。
応答には24 kHz、モノラル、60 msフレームのOpusテスト音を使用します。
受信と再生を交互に繰り返し、デバイスの入出力コールバック、接続状態、XSの計測値を記録します。
外部サービスによる音声認識、応答生成、文字起こしの品質は、この試験には含まれません。

ChatAudioIOは1,800秒の終了マーカーまで動作し、入力コールバック40,952回、出力コールバック6,027回を記録しました。
サーバーからは5,190パケットのテスト音を送信しました。
通常動作中のシステム空きメモリは約6.15から6.17 MBで推移し、全計測中の最小値は6,147,279バイトでした。
173区間のエンコード統計すべてで`dropped_pcm=0`でした。

一方、サーバーが10秒ごとに記録したマイク受信間隔には最大17,978 msの値がありました。
同時期のpingは60回中58回応答し、RTTは最小2.227 ms、平均68.157 ms、最大604.289 msでした。
PC側TCP統計にも再送がありました。
継続動作は確認できましたが、低遅延で安定した音声通信の合格判定は保留します。
同一環境での旧SDKとの比較を行っていないため、SDK更新が原因とは断定できません。

Web RadioはSomaFMのHTTP MP3ストリームを使用し、最初の再生通知から1,801.17秒後に42,208バッファまで進んだことを確認しました。
32バッファごとの再生ログの最大間隔は1,411 msで、エラーと再接続はありませんでした。
再生期間中のシステム空きメモリは7,143,099から7,151,759バイトでした。
専用アプリのため、通常ホストのUIやサーボとの同時稼働はこの再生試験に含まれません。

Web Radio再生中の追加測定では、デバイスへのpingは60回すべて応答し、ルーターへのpingは60回中59回応答しました。
最大RTTはそれぞれ1,030.901 msと1,062.582 msでした。
PCとルーター間にも遅延と応答欠落があるため、音声遅延の比較試験では無線環境を揃える必要があります。

## 手動確認が必要な項目

画面の見た目、タッチとボタンの操作感、実際の首の動きと異音、LEDの見え方、音切れと音質は未確認です。
USB音声、USB給電とバッテリーの切り替え、明るさ、電池表示、手動再起動も別途確認が必要です。
音声コールバックの進行だけでは、スピーカーから正常な音が出たとは判定できません。
M5StackChan CoreS3以外の基板の実機動作は、この記録の対象外です。
