# CoreS3のPodcast再生時の再起動

## 原因と修正範囲

M5StackChan CoreS3でPodcastを一時停止し、約2分先へシークして再開すると、端末が再起動した。検証の基準は、PR777とPR778の統合SHA `8903e0cf933d445d67d3e84d1cac790022e9e1c2` とModdable SDK10.1.0、ESP-IDF6.1である。

基準SHAに診断用のabort表示とCスタックの取得処理を加えると、再生開始時にも `XS abort: native stack overflow` が再現した。再起動するタスクは `main` で、バックトレースには `fxCheckCStack` と、GCの `fxMarkValue` / `fxMarkInstance` の再帰が含まれていた。MP3デコード用Workerのスタックとは別の不足である。最初にユーザーが観測したシーク後の再起動と、診断中の再生開始時の再起動は、再現条件を分けて記録する。

ESP32のplatform manifestで、CoreS3のホストを実行するCタスクに15KiBを割り当てる。対象は `m5stack_cores3`、`m5stackchan_cores3`、`stackchan_rt`。SDK既定の10KiBから固定メモリが5KiB増える。JavaScriptのスタックスロット数、XS chunk容量、MP3 Workerの設定は変更しない。PR777のWhisper対応と同じ設定に揃える。

この容量は実機のGC処理を含めて検証する。manifestの数値だけを照合するテストでは、必要なスタック量や将来のオブジェクトグラフの変化を検知できない。

## 再現・確認手順

1. ホストとMedia Player MODをreleaseでビルドする。sanoTTSを使う構成では `npm run build:sanotts -- --mode=release` を使う。
2. 対象端末の占有状態を確認してホストとMODを書き込む。NVSを消去せず、設定済みのWi-Fiで接続する。
3. PodcastでNPR News Nowのエピソードを選び、再生位置が進むことを確認する。
4. 一時停止し、シークバーを約2分先へ移動して再開する。移動した位置から再生が進むことを確認する。
5. もう一度一時停止・再開し、停止する。同じ起動状態で繰り返す。

未取得の位置へのシークでは、HTTP Rangeの利用可否と取得済みチェックポイントによって先頭からMP3フレームを走査する場合がある。バッファ待ちと端末の再起動を区別し、待ち時間も記録する。

## X1での検証結果

2026-11-12、Linux上の専用SDKと、M5StackChan CoreS3の `/dev/ttyACM0` で確認した。既存の作業ツリーとSDKを変更せず、別worktreeを使った。NVSとモデル領域は消去していない。

| 構成 | 結果 |
| --- | --- |
| 基準SHA、既定10KiB、診断用abort表示とCスタック取得 | 再生開始時にmainタスクのnative stack overflowを確認 |
| 基準SHA、16KiB、同じ診断ホスト | 再生・一時停止・約2分先へのシーク・再開・再度一時停止と再開・停止を2周完了。スタック最低空き量4,424 bytes |
| 基準SHA、15KiB、受信量と走査位置を記録する診断ホスト | 同じ操作を2周完了。スタック最低空き量3,720 bytes。再起動なし |
| 15KiBの製品sanoTTSホスト、製品のPodcast各module・フィード設定 | Piuのタッチ操作による同じ手順を2周完了。再開後に再生位置が進み、停止後は0へ戻る。再起動なし |

上記の操作は、製品のPodcast画面へPiuのタッチイベントを送る診断MODで実行した。診断MODにはcontrollerの観測参照と自動操作を加えているため、通常MODそのものの試験とは区別する。

最後の製品ホストの試験では、controllerの差し替えと観測参照も外した。MODの起動入口に自動操作だけを追加し、画面の再生位置とボタンを観測した。ホストは基準SHAに先行する型参照・Drawer修正と今回の15KiB設定を反映した構成で、PR777の後続の通信修正全体は含まない。ホストイメージのSHA-256は `77aa611e09e28518e03007018e96982807e393a371f301532c0e68f0b9216789`。

シーク後の最初の45秒制限ではバッファ待ちのまま試験を終了した。制限を延ばすと再開した。15KiBの計測では、受信量とMP3フレームのチェックポイントが移動先へ向かって増え、PCMの出力位置が約119秒から進むことを確認した。待ち時間の短縮や通信品質の改善は、このスタック容量の修正には含めない。

PR778のホストで、architecture 76件、6ターゲットのmanifest検査、lint、formatが成功した。MediaPlayerとPodcast UIのXS試験2本、Gallery定義のNode試験14件も成功した。Podcast UI試験はBehaviorの直接呼び出しをPiuのタッチイベントに置き換えている。このXS試験だけでは、実機のCスタック容量を検証できない。

標準ホストとsanoTTSホスト、Media Player MODのreleaseビルドは成功した。Media Playerの製品XSAはGallery公開物と全バイト一致し、ソースとGalleryのREADMEを併せて更新した。

外部の503試験URLは実機ではHTTP402を返した。この応答で `retrying` 通知、`stop()` と `done === 'stopped'`、停止後5秒間の通知停止は確認できたが、想定した503の試験成功としては数えない。

続いてX1内のHTTPサーバーで、最初の要求に503を返し、次の要求ではMP3を768KiB送って切断し、3回目の要求を正常に受け付ける試験を実行した。製品sanoTTSホストと実際の再生APIで、503後の `retrying`、再生開始後の切断に対する2回目の `retrying`、復帰後の `playing` と再生位置の進行を確認した。別の503を返し続ける要求では、再接続待ちで `stop()` を完了し、`done === 'stopped'` と停止後5秒間の通知停止を確認した。サーバーの要求記録でも停止後の追加要求はなかった。PR778の再接続通知修正を含む実機での確認結果である。

同じ製品ホストで、Rangeとvalidatorを提供する音源と、Range・validatorを提供しない音源も各3周、計6周確認した。再生・一時停止・約2分先へのシーク・再開・再度一時停止と再開・停止が完了し、再起動はなかった。サーバー側でも前者の206と後者の200による取得を確認した。この追加試験はフィード設定とcontroller観測を含む診断MODで実行した。終了時は自動操作・観測を含まない通常のMedia Player MODへ戻した。

APIキー未設定のためオンライン会話はユーザーの指定により未実施。基準SHAではSpeakの再試行4回について、ユーザーから発話・口パクが正常で、音切れと再起動がなかったとの報告を得た。15KiB構成の聴取評価、長時間運転、基準SHAで最初に一度だけ報告されたSpeak再起動の原因確定は未完了として残る。
