# Podcastの遠方シーク待ち短縮

Issue #798 の対応。未取得位置までのMP3を受信してフレームを数える待ち時間を、固定ビットレート候補に対するRange取得で短縮する。

## 精度と利用範囲

メディアAPIの `seekAccuracy` は既定で `'exact'`。Podcastは `'approximate'` を指定する。取得済みの近い正確なチェックポイントがあれば、その位置からの走査を優先する。

先頭から128フレームのビットレート・サンプルレート・MPEG形式が揃った場合に、CBR候補を保持する。検証用のETagまたはLast-Modifiedと総byte数があり、正確な索引から離れた場所へ移動するときは、目標の約2秒前のbyte位置を概算して取得する。3連続のフレーム境界を確認し、同期したbyte位置から推定時刻を計算してプリロールを行う。

先頭の観測だけで、音源全体がCBRだとは保証できない。途中に隠れたVBRがある場合、移動先の時刻に誤差が出る。`positionEstimated` はこの位置の推定を表し、UIは現在位置に「約」を付ける。既存の `estimated` はdurationの推定を表す。出力開始やEOFを根拠に、推定位置を正確な時刻へ昇格させない。

## 再開と例外

- 推定起点から実際に確認したチェックポイントは、正確な索引と分けて保持する。一時停止・再開では同じ推定時刻系を使い、明示的なシークではその推定索引を破棄する。両索引の合計上限は512件。件数上限は増やさないが、推定位置を識別するfieldが加わる。
- 出力前の同期失敗やCBR不一致は、一度だけ正確な索引または先頭からの取得へ戻す。通信失敗は通常のエラーとして扱い、この再取得で覆い隠さない。
- 出力後にVBRを観測した場合は、音声を再生し続け、将来のCBR外挿を無効にする。取得済みの推定索引は通常の再開に使える。同じvalidatorが続く間、CBR候補を再学習して復活させない。
- Range要求に200が返った場合は、同じ応答を先頭時刻0から処理する。206で総byte数や対応するvalidatorが矛盾する場合は、内容変更として失敗する。
- Range非対応、validatorなし、VBRと判明した音源では、従来のフレーム走査の待ち時間が残る。

推定位置からのシーク・再開は64KiBの圧縮データを先読みする。プリロール中もこの待機を維持し、EOFでは残りが64KiB未満でも出力する。正確なシークとライブ音源の開始条件は変更しない。新しいbufferを割り当てる変更ではなく、既存buffer内の出力開始条件を変える。

## 比較方法

M5StackChan CoreS3、Moddable SDK10.1.0、ESP-IDF6.1を使用。基準はPR778の `2aef67db495a9f81adeb711fb4b84be0329f166c` 相当のメディア処理を含む、15KiB Cスタックの統合sanoTTSホスト。比較する候補も同じsanoTTS構成を使い、SDK、保存設定、音源、配信速度、音量、操作用MODを揃える。

固定したNPR音源は4,587,136 bytes、ID3 34 bytes、10,975フレーム、44.1kHz・128kbps。PC側で全フレームを独立に走査し、286.693877551秒の時刻・byte索引を作った。Xing/Info/VBRIの索引はない。

試験サーバーの上限を32KiB/sとし、10秒再生→一時停止→120秒へシーク→再開を5回行う。再開呼び出しから、実際に消費されたPCMが進捗へ反映されるまでを測る。`seek()` の完了や表示位置の変更を再生開始として数えない。測定には進捗通知とポーリングの分解能が含まれ、スピーカーの実音を録音した測定ではない。

位置精度は表示値だけで判定しない。診断用の候補ホストが記録する最初の出力フレームのbyte位置と、フレーム内で捨てたsample数を、PC側の全フレーム索引に照合する。診断用traceは製品版から除く。

合格の目安は中央値5秒以内、最大10秒以内、基準の中央値から80%以上短縮、固定CBR音源のフレーム時刻に対する誤差250ms以内とする。この位置誤差は試験音源の結果であり、任意のCBR候補やVBR音源に対する保証ではない。

## 実機結果

2026-11-12〜13、同じ端末・音源・32KiB/sのサーバーで比較した。

| 構成 | 5回の待ち時間 | 中央値 | 最大 |
| --- | --- | --- | --- |
| 変更前 | 55.532 / 56.582 / 82.093 / 67.296 / 55.530秒 | 56.582秒 | 82.093秒 |
| 診断版・先読み調整前 | 2.622 / 2.642 / 3.080 / 2.851 / 2.546秒 | 2.642秒 | 3.080秒 |
| 最終版・64KiB先読み | 4.030 / 4.030 / 6.081 / 4.330 / 5.580秒 | 4.330秒 | 6.081秒 |

最終版の中央値は約92.3%短縮した。5回のシークを完走し、最後の試行では通常の再開と前後へのシークも確認した。停止後のcallbackがなく、再起動もなかった。

位置精度は上表の診断版で別に測った。最初の出力フレームとフレーム内の破棄sample数をPCの独立索引へ照合した結果、今回の固定音源では120秒に対する誤差は全回1ms未満だった。最終版も同じbyte・時刻計算を使うが、最終版の待ち時間と診断版の精度は別の測定である。これはMP3フレーム時刻との照合であり、エンコーダー遅延やスピーカー実音の精度を測定した結果ではない。

先読み調整前の製品UI試験では、停止・再開などの操作は完了した一方、underrunが3回あり、61.705秒のwall timeに対して再生位置は55.04秒しか進まなかった。品質基準を満たさないため、Astraと相談して固定64KiBの開始前先読みを採用した。最終版はPiuのタッチ操作で2周を完走し、シーク後の再開は5.369秒と4.416秒、通常の再開後は60.007秒に対して60.032秒進んだ。underrunログは0件で、現在位置の概算表示と停止後の表示解除も確認した。聴取による音質評価とは区別する。

公開NPR配信でも同じUI操作を2周完走した。シーク後の再開は9.115秒と8.317秒。通常の再開後は60.063秒に対して60.032秒進み、underrunログは0件だった。公開配信では通常の再開に11.316秒かかった回もあり、通信・TLSを含む待ち時間を一定の秒数へ保証する変更ではない。

Rangeを無視して200を返す固定音源と、Xingあり・なしの実VBR音源でも、再生・一時停止・シーク・再開・停止を各1回完了した。再開後の位置は推定扱いにならず、再起動とunderrunログはなかった。これらはfallback経路の回帰確認であり、待ち時間短縮の測定には含めない。

この最初の案で合格基準を満たしたため、TOCジャンプ、独立した先読み索引、SDキャッシュの追加は行わない。SDカードへのファイル作成・変更も必要ない。VBRやRange非対応音源の待ち時間を一律に短縮した結果ではなく、これらは既存の走査経路を維持する。

初期の試験サーバーは1KiBの送信bufferでTCPの遅延ACKの影響を受け、配信が遅くなった。この条件の失敗した試験は比較から除外した。上表はTCP_NODELAYと64KiB以上の送信bufferを使い、先払いで配信速度を制限した同一条件の結果である。

先読み調整前の製品版では、HTTP 206応答後に `Media request timed out` で失敗した試行が1回あった。同じ版を再起動して5回完走し、最終版も5回完走した。TCPの再送は観測したが、このtimeoutの原因を確定した結果ではない。失敗ログも保持し、成功した試行だけで通信の安定性全般を保証しない。
