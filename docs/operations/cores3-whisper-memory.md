# CoreS3の録音終了時の再起動

## 症状と原因

Wi-Fi接続後、AI会話MODの「押して話す」を離すと端末が再起動した。CoreS3の実機では、WhisperのHTTPS要求開始時に `XS abort: native stack overflow` を記録した。Moddable SDK10.1.0の製品構成は、XSを実行するCタスクに10KiBのスタックを割り当てる。これはJavaScriptのスタックスロット数とは別の容量である。

録音バッファにも別の不足があった。会話MODの上限194,560 bytesとWAVヘッダー44 bytesを通常のUint8Arrayで確保すると、固定262,144 bytesのXS chunk領域をほぼ占める。独立したXSテストでは、この録音を保持しながら上限内の約30KiBのJSON応答を処理すると `XS abort: memory full` が再現した。実機で観測した直接の再起動原因はCスタック不足であり、このヒープ不足とは区別する。

## 修正

- 録音をSharedArrayBufferで確保する。録音中の約190KiBをXS chunk領域の外へ配置し、HTTPとJSON処理の領域を確保する。総メモリ使用量が減る変更ではない。closeは所有参照を外し、送信中の参照もなくなった後にGCが実体を回収する。
- HTTPSの初期化前にPromiseの継続へ移り、呼び出し元のCスタックを解放する。これだけでは実機の10KiBスタック不足は解消しなかった。
- 3種類のCoreS3プラットフォームで `creation.nativeStack` を15KiBにする。Cタスクの固定メモリを5KiB増やす。JSスタック768スロット、XS chunk容量、PCMフレームの処理、モジュール分割、公開I/Fは変更しない。

## 検証

2026-11-12、M5StackChan CoreS3、COM6、Moddable SDK10.1.0、ESP-IDF6.1、PR777とPR778の統合構成で確認した。

| 構成 | 結果 |
| --- | --- |
| 10KiB Cスタック、通常の録音バッファ | 録音終了後に再起動 |
| 10KiB Cスタック、SharedArrayBuffer、HTTPS初期化の非同期化 | HTTPS要求開始時にnative stack overflow |
| 15KiB Cスタック、同じ録音・HTTPS修正、計測ホスト | 5.5秒の録音を文字起こしでき、再起動なし。実行タスクのスタック残量の最小値は4,212 bytes |
| 診断用abort hookとネイティブ計測を除いた製品版ホスト | 5.5秒録音後、文字起こし、LLM応答、音声再生、会話ターンのcompletedを確認。起動回数は増加しなかった |

繰り返し試験では再起動はなかったが、別の受信キュー上限により `Responses consumer is too slow` で会話が失敗した。Cスタックと録音バッファの修正だけで全ての会話失敗が解消したとは判断しない。

回帰テストは、実Whisperアダプターの要求開始前のキャンセル、送信量の上限、共有バッファのoffset、HTTP失敗、タイムアウトを検証する。XSの固定chunkテストは上限の録音とJSON応答が共存できることを検証する。NodeだけではESP32のCスタック不足を検出できないため、実機の録音終了と再起動ログを別に確認する。

実行コマンドはfirmwareディレクトリで `npm run test:unit` と `npm run test:moddable -- host/modules/voice/__tests__/whisper-memory-device/manifest.test.json`を使う。メモリ回帰テストは `host/modules/voice/__tests__/whisper-memory-device/manifest.test.json`、HTTP回帰テストは `host/modules/audio/__tests__/whisper-request.test.ts` にある。

他のCoreS3機種、RealtimeConversationとの同時負荷、長時間連続使用のメモリ余裕は未計測である。4,212 bytesはこの試験中の観測値であり、全処理の最大スタック深さを保証しない。

## LLM受信の待ち合わせと失敗時の停止

再起動対策後の繰り返し試験で、読み上げを待つ間にLLMの受信キューが満杯になる別の不具合を確認した。受信コールバックごとに全バイトを読み込む方式を、1つのチャンクの処理が終わるまで次のreadを待つ方式へ変更する。1回の読み込みは設定された受信予算と4,096 bytesの小さい方を上限とし、未処理チャンクを積み重ねない。SSEイベント自身のサイズ上限も維持する。

SDKのonReadableは、その時点の未読バイト数を通知する。通知のたびに加算せず最新値に置き換える。SDKがonDoneを通知した後はrequestを読まず、すでに受け取ったデータの解析を待って終了する。キャンセルとタイムアウトは、音声側の待ちが解けなくてもHTTPを閉じる。

会話ターンが失敗した場合は、出力の破棄前にそのターンのscopeをabortする。遅れて残った読み上げ処理にも停止を伝え、ターンの状態はfailedとして報告する。意図したユーザー割り込みとの区別を保つ。

回帰テストでは、従来の受信数・バイト数上限で失敗するバーストを再現し、修正後の待ち合わせ、通知回数によらないバイト列の一致、EOF、切断、キャンセル、タイムアウトを確認した。失敗したターンに音声処理が残るケースも修正前に再現し、停止→出力破棄→音声セッション解放の順序を確認した。

## 受信修正後の構成の確認結果

製品版ホストのSHA-256は `3decd4e8e26153d933b286509db85d07f2275c60fc0377554e43419aaaa5cce5`。診断用のabort hookとネイティブ計測は含めていない。ホスト内のLLM・TTS実装で同じ起動中に3回のテキスト入力を試し、1回はLLMからsanoTTS再生まで完了、2回は最初のLLMイベントの前にタイムアウトした。起動回数は増加しなかった。別の5.5秒の実マイク録音でも、解放後の再起動はなかった。

通信タイムアウトは残っている。端末では−87〜−89dBmのRSSIを観測したが、電波だけが原因とは確定していない。再起動の修正と、通信を含む連続会話の安定性は分けて評価する。

- 親PRのNode検証は、`test:unit`のテストコマンドに `--test-concurrency=1` を指定し、656件成功、失敗0件。並列のテスト用モジュール生成で既知の競合があるため、標準の並列実行とは区別する。
- ストリーミングPRの標準 `npm run test:unit` は675件中662件成功、13件スキップ、失敗0件。
- 固定XS chunkでの録音・JSON応答の回帰テスト、Piuによる押下・解放・会話終了のテストは成功した。
- 受信量、キャンセル、失敗したターンの音声停止を独立レビューし、P2以上の指摘はなかった。

実機はPR777とPR778の統合構成であり、PR779固有のflush実装を含むホストは今回の実機試験対象にしていない。

追加の通信段階の計測では、同じ製品版ホストに計測用MODを載せ、3回連続でHTTP200、LLM応答、sanoTTS再生、turn.endedのcompletedを確認した。起動回数は43のままで、最後のRSSIは−66dBmだった。この試験は、ホストと同じ受信実装をMODに複製して接続段階を記録したものなので、前述のホスト内の実装による試験と区別する。試験後は計測と自動入力を含まない通常のai_stackchan MODに戻した。電波が弱い時のタイムアウトが解消したと断定する根拠にはしない。

## 通信中の描画を停止する

書き込みを停止してユーザーが2回操作した再試験では、再起動はなく、画面にprovider_failedが表示された。通信エラーと、書き込みによるリセットを区別する。

AI会話MODは、録音を離した直後、Whisperへの送信が始まる前に顔の定期更新を停止する。呼吸と瞬き、動く装飾を停止し、以前の吹き出しも閉じる。押して話すボタンと音声クレジットは残す。今回は口も閉じた静止状態とし、口パク用のタイマーやPCM監視は追加しない。

終了・失敗・中断後に通信待ちが残っていなければ、停止前の顔アニメーション設定を復元する。次の録音が文字起こしを待っている間は、前のターンが終了しても静止を続ける。非表示または停止済みだった装飾を復元時に勝手に動かさない。ホストの `ui.faceMotionEnabled` で元の状態を取得するため、ホストとMODを合わせて更新する。

描画停止の効果をCPU使用率の数値では計測していない。通信タイムアウトの原因を描画負荷と断定するものではない。

描画停止版は、Piuによる会話MODの回帰テストと、実際のEmoticonを使うface-view-stateテストが成功した。通常のリアクション由来の装飾も対象にし、通信中の追加・再追加、非表示または停止済みの状態の復元を確認した。独立レビューのP2以上の指摘を解消済み。ホストのSHA-256は `a59c3dd9704adead94b13b02ebf5776ef39c642cbb05a66b9cb6199913afad6a`。CPU使用率と通信成功率の改善は、このテストからは判断しない。

## 中断後の接続とエラーコード

描画停止版をユーザーが繰り返し操作したところ、再起動はなくなったが、数回に1回のprovider_failedが残った。調査では、名前解決中にWhisperやクラウドTTSを中断・タイムアウトした後、遅れて返った名前解決結果からTLS接続が作られる不具合を別途再現した。SDKのHTTPClient.closeは未完了の名前解決をキャンセルしないため、Responsesで使用しているcreateClosingClientを音声のHTTP要求にも使用する。名前解決自体の完了は待つが、閉じた要求のコールバックから接続を作らない。

会話処理では、AgentResult.failedの既知のエラーコードを保持する。たとえばLLMがdeadline_exceededを返した場合、画面の通知にもそのコードが届く。文字起こしの境界で渡された既知のコードも保持し、未知の値はprovider_failedにする。提供元のメッセージは内部の中断理由だけに保ち、画面のイベントには含めない。Whisperアダプターは失敗理由を文字列で返すため、その段階ですでにprovider_failedになったタイムアウトを、この修正で分類し直すことはない。

接続の後処理とコードの保持は、修正前の失敗を回帰テストで再現してから修正した。親PRの新しいNode検証は、TypeScriptをコンパイル後にtest:unitのテストコマンドを直列実行し、663件成功、スキップ0件、失敗0件。固定XS chunkの回帰テストも成功した。独立レビューでP2以上の残件はなかった。これらは接続の寿命とエラー伝播の検証であり、実機の断続的なprovider_failedの原因が解消したと断定する根拠にはしない。


実機の追加切り分けでは、描画停止版の統合ホストにabort理由の表示だけを加え、ホスト内の実LLMとsanoTTSを4回続けて呼び出した。1回目はLLMの最初のイベント前に45,244msでdeadline_exceededとなり、TTS.openは呼ばれていない。2〜4回目は10〜14秒で再生まで完了した。失敗回の開始時RSSIは−87dBm、成功回の開始時は−86、−69、−69dBmだった。電波の弱さとの関係は疑われるが、この4回だけで原因は確定しない。LLMの45秒の期限には、応答イベントを受け取った後の読み上げ待ちも含まれるため、一般にdeadline_exceededだけでネットワーク障害とは判定できない。

この直前の診断MOD試験では、1回成功した後にソフトウェアリセットを1回記録した。abort表示を有効にして同じ試験を行った4回では再現しなかった。通常MODに対するユーザーの「再起動しなくなった」という観察とは分けて記録し、診断中のリセット理由は未確定とする。


続いてホストと同じLLM通信実装を診断MODに複製し、名前解決、HTTP送信開始、応答ヘッダーを記録した4回は、すべてHTTP200と再生完了だった。さらに既存の低遅延leaseを診断MODだけで交互に取得し、実際のWi-Fiモードを確認した。min-modemの2回は11.962秒・24.229秒、noneの2回は30.228秒・11.654秒で、いずれも再生まで完了した。ツール呼び出し回数も2〜3往復と揺れるため、総時間だけから省電力の影響を比較できない。省電力を原因とする根拠は得られず、製品側のWi-Fi設定は変更していない。

後処理・エラー伝播修正後の通常ホストはPR777とPR778の統合構成で、SHA-256は `7ed623f87a3ba076eaa675bf32f4b4b474d8754c8aa4844bf5be80b0f18fc07b`。診断用abort表示や自動入力を製品版へ取り込まない。PR779は親の修正を取り込み、標準の並列Node検証で682件中669件成功、13件スキップ、失敗0件だった。PR779固有のflushホストは実機未検証である。
