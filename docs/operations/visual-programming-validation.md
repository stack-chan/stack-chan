# Visual Programming評価手順

## 評価対象

評価対象は、ローカルSDKを使ったことがない参加者です。

参加者ごとに新しいブラウザプロファイルを用意します。

評価者は操作方法を説明せず、チュートリアルの場所だけを伝えます。

## 計測する時点

- エディタを開いた時点
- 最初のビルドに成功した時点
- 最初のシミュレーター実行に成功した時点
- 最初の実機書き込みに成功した時点
- ビルド、USB接続、互換性確認に失敗した時点

エディタはこれらの時点をブラウザ内へ記録します。

評価終了後にヘッダーの評価ログ保存ボタンからJSONを保存します。

## 合格条件

- 15分以内にサンプルの表情か発話を変更し、シミュレーターで再実行できる。
- 対象機種にない能力を配置した場合、実機書き込みより前に理由を確認できる。
- 実行時エラーが発生した場合、対応するブロックへ戻れる。
- 実機書き込み前にチップ、パーティション、サイズ、使用能力を確認できる。
- 書き込み済みMODをバックアップから復元できる。

## 記録

評価ログにはブラウザ識別文字列が含まれます。

公開レポートへ転記する場合は、個人を識別できる拡張機能名や管理情報が含まれていないことを確認します。

複数参加者のログは、最初のシミュレーター実行までの中央値と失敗種別ごとの件数を集計します。

ログを同じディレクトリへ集め、次のコマンドで集計します。

```sh
cd web
npm run metrics:aggregate -- participant-1.json participant-2.json
```

集計結果には、参加者数、15分以内のシミュレーター成功数、最初のシミュレーター実行までの中央値、ビルド失敗数、実機失敗数が含まれます。

## CoreS3実機検証記録

2026年7月15日に、`/dev/ttyACM0`へ接続したM5Stack-chan CoreS3を次の条件で検証しました。

- チップはESP32-S3 rev 0.2、フラッシュは16 MiB、接続はUSB-Serial/JTAGだった。
- factoryアプリは`xs_esp32 8.3.0-1-gacf3d5262-dirty`で、対応するMODのXS版は17.8.0だった。
- `xs`パーティションはoffset `0xfa0000`、size `0x40000`で、接続時の先頭4 KiBは全`0xFF`だった。
- 接続時の先頭4 KiBを退避し、SHA-256 `f47a8ec3e9aff2318d896942282ad4fe37d6391c82914f54a5da8a37de1300c6`を記録した。
- 2,491バイトのXS 17.8.0アーカイブを書き込み、アプリ起動前の読戻しが書き込み元のSHA-256 `1d6fd2e6be787276512b068cce48223843a5b16923897ee4bbe8a4da38d9c156`と一致した。
- 再起動後に通常アプリが`[main] app context created`、MODが`[vp-hardware] mod ready`、通常アプリが`[main] app behaviors ready`の順で出力し、10秒間に例外や再起動ループが発生しないことを確認した。
- 起動後に読み出したアーカイブでは、XSランタイムによる識別子マッピングで`IDEN`とバイトコードが更新されていた。
- 起動後のアーカイブをバックアップし、MOD削除後の先頭4 KiBが全`0xFF`であることと、通常アプリがMOD固有トレースなしで起動することを確認した。
- 起動後バックアップを復元し、読戻しがバックアップと一致することと、`[vp-hardware] mod ready`が再度出力されることを確認した。
- 最後に接続時の先頭4 KiBを復元し、接続時と最終状態のSHA-256が一致することと、`SPI_FAST_FLASH_BOOT`でMODなしの通常アプリが起動することを確認した。

実機検証では、esptool v5.3.dev2 CLIを使い、WebSerial実装と同じ順序でパーティションテーブル、factoryアプリ記述子、既存MODを読み、書き込み、起動前の読戻し照合、再起動、削除、復元を実施しました。

シリアル制御線の状態によって一度ダウンロードモードへ入ったため、DTRを解除したままRTSでENをパルスし、通常起動へ戻したことも確認しました。

## 検出した既存の全デバイスビルド問題

Visual Programmingの対象機種であるCoreS3系とは別に、従来機種を含む`npm run bundle`で次の問題を検出しました。

- `com.m5stack`は4 MiB構成のfactory app partitionを`0x154dc0`バイト超過するが、`mcconfig`は終了コード0を返し、超過したバイナリがバンドルへ含まれる。
- 基準ブランチ`origin/develop`でも同じビルドが`0x157fd0`バイト超過するため、Visual Programmingによる回帰ではない。
- `com.m5stack.fire`は`embedded:io/audio/in`を解決できず、基準ブランチとVisual Programmingブランチの両方でビルドに失敗する。
- `mcbundle`はFireの失敗後も終了コード0を返し、Fireの空ディレクトリをZIPへ含める。

このため、CoreS3系の個別ビルドは合格ですが、全デバイスバンドルは合格扱いにしていません。

評価参加者による15分指標の測定も未実施です。

Webとファームウェアは、開発依存を含む`npm audit`で脆弱性0件です。
