# STTとTTSのストリーミング契約

音声の入力、認識結果の通知、音声の出力を別々に扱います。各プロバイダーは共通の開始・終了操作を提供し、通信やネイティブ処理の違いを内部で吸収します。共通のインタフェースを持っていても、途中結果を返せるかどうかは実装によって異なります。

## TTSは入力を閉じずに音声化できる

`TTS.open()`で作った1つの`Synthesis`に、文章を順に渡せます。`output`はセッション中ずっと同じ音声源です。

| 操作 | 完了時に保証すること |
| --- | --- |
| `write(text)` | 文章を受け付けた。音声化や再生の完了は保証しない |
| `flush()` | ここまでの未処理の文章を音声化し、PCMを接続先に渡し終えた。入力と出力は開いたまま |
| `finish()` | 入力を閉じ、残りの文章を音声化し、出力を終了した |
| `close()` | 中断して、HTTPやネイティブ処理の終了を待った |

たとえば、LLMが最初の文を返した時点で`write()`と`flush()`を呼びます。その文の音声を出力した後も、次の文を同じセッションに追加できます。

```text
open
  write("こんにちは。") → flush → 最初の文のPCM
  write("今日は何をしますか。") → finish → 次の文のPCM → 出力終了
close
```

音声の接続は最初の`flush()`や`finish()`より前に行います。音声源は、あとから接続した利用者のために過去のPCMを保存しません。

`flush()`と`finish()`は、スピーカーから音が出終わるまで待つ操作ではありません。再生完了は`PlaybackSink.finish(outputId)`で待ちます。合成を終える責任はTTS、物理的な再生を終える責任は音声出力側にあります。

`write()`と`flush()`は、前の操作を`await`してから呼びます。競合する操作は`device_busy`になります。`finish()`は進行中の`flush()`を引き継げますが、進行中の`write()`とは競合します。受理された`finish()`を繰り返し呼ぶと同じPromiseを返します。

## 対応するプロバイダー

OpenAI Speech、内製StackchanVoice、sanoTTSで同じ`Synthesis`を使えます。StackchanVoiceのKoe入力とsanoTTSのかな入力も同じ操作を持ちます。

OpenAI Speechでは、空でない`flush()`ごとにHTTPリクエストを作ります。1本の双方向接続に文章を送り続ける方式ではありません。各リクエストから受信するPCMは、全体の受信を待たずに下流へ渡します。

ローカルTTSでは、既存のネイティブ合成処理を区間ごとに呼びます。区間の合成器が出すPCMバッファをそのまま転送し、このラッパーでは音声全体のコピーや蓄積を行いません。下流がPromiseを返した場合は、その完了まで生成側を待たせます。下流が同期的に受け取れる場合は、PCMの転送を同期的に進めます。

1セッションの文章は合計4096 UTF-16コード単位、空でない合成区間は64個までです。1区間はOpenAI Speechで4096、StackchanVoiceで2047、sanoTTSで512コード単位までです。Koe入力には、これに加えてネイティブ実装のUTF-8バイト数制限があります。上限を超える入力は`resource_exhausted`として拒否し、無制限の待ち行列には積みません。

`textAt()`は、再生位置までに出力を完了したと確認できる文章の先頭部分だけを返します。OpenAI Speechのように対応関係を確認できない実装では`unknown`になります。合成完了と、聞き手がその文章を聞き終えたことは区別します。

## STTの途中結果は文章全体の更新

`STT.open()`が返す`input`はPCMを順次受け取れます。認識結果は`onTranscript`へ通知します。

```text
{ utteranceId: "u1", text: "きょうは", final: false }
{ utteranceId: "u1", text: "今日は晴", final: false }
{ utteranceId: "u1", text: "今日は晴れ", final: true }
```

`text`は同じ発話についての最新の文章全体です。差分ではないため、表示側は前の文章に連結せず置き換えます。入力を確定した後に`final: true`を一度だけ通知します。途中結果を返さないプロバイダーも、この契約を満たせます。

現在のWhisper実装は、上限付きのバッファに録音し、`finish()`でまとめて送信します。この変更でネットワークへの逐次送信や途中認識は追加していません。`finish()`の重複呼び出しによる二重送信を防ぎ、`close()`後に遅れて返った認識結果を通知しないようにしています。

## 会話パイプラインへの影響と移行

既存のCascadedConversationは、LLMが返した文章を文ごとに合成して再生する構成を維持します。新しい`flush()`を使った単一セッション化や、次の文の先読み合成は行いません。STTの途中結果はイベントとして通知し、Agentには確定した文章を渡します。

独自のTTS実装は、`Synthesis.flush()`の追加が必要です。`flush()`を単に`finish()`の別名にすると、その後の入力を受け付けられず契約を満たしません。単発の合成器を再利用する場合は`openStreamingSynthesis()`で包めます。内部の合成器は、渡されたPCMを下流が受け取るまでバッファを再利用せず、`close()`で処理と資源の解放を完了させてください。

この変更はTypeScriptの公開契約を変えます。保存済みの設定やモデルの形式は変わりません。組み込み機器の性能への影響は実機で別途確認する必要があります。
