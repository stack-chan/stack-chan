# StopWatch Worker TTS: 途中切断と文節内の途切れを分けた実機試験
2026-11-18 | 変更 d92202e9 / 専用実験ブランチ。課金API・会話音声を使わず、同じ端末・画面・スピーカー経路をミュートして比較。

## 何が起きていたか
鍵を使わないLAN内TLSサーバーで、6,000 ms（288,000バイト）または1,200 ms（57,600バイト）の24 kHz/mono/S16 PCMをSSEで送信した。1イベントは5,760バイト。送信は最速か、120 ms間隔に小さな揺らぎを加えたもの。ホスト側とWorker側ともTLS 1.2で証明書を検証し、短い音声・長い音声とも同じ内容を使った。実機でキューに入ったPCMバイト数と、各PCMブロックの先頭・末尾のサンプルを確認した。

- **終端の取りこぼし。** 従来のWorker版は、短い音声を完送後すぐ切断すると、HTTP 200でも完了SSEに一致する83バイトを読めず、失敗。改行探索だけを高速化しても同じ83バイトを失った。サーバーが「最後のバイトを送信し終わった後のソケット切断」だけを15秒遅らせた対照では、短・長×2速度の4/4で全音声と終端が届いた。15秒は再生待ちではない。
- **供給の遅さ。** 切断を遅らせて成功させた従来版でも、実時間送信の6秒音声に10.13秒（開始から再生drain完了まで）かかり、全DMA枠が書込可能だった通知は65回。この条件では、WANや音声生成サービスがなくても再現した。

## 段階比較：6秒の音声
| 送信・計測 | 従来探索＋旧キュー | ネイティブ探索だけ | 統合版 1回目 / 2回目 |
|---|---:|---:|---:|
| 最速送信：完了時間 | 10.26 s | 8.98 s | 7.45 / 7.45 s |
| 最速送信：全DMA枠が空いた通知 | 64 | 54 | 0 / 2 |
| 実時間送信：完了時間 | 10.13 s | 8.34 s | 7.45 / 7.45 s |
| 実時間送信：全DMA枠が空いた通知 | 65 | 35 | 6 / 2 |
| 実時間送信：初回PCM | 985 ms | 967 ms | 960 / 959 ms |
| 実時間送信：改行探索 合計 | 1,717 ms | 56 ms | 47 / 59 ms |

従来・探索のみは各条件1回、ソケット切断は完送15秒後。統合版は各条件2回、完送即切断。表の時間には接続・TLS・初回PCM待ち・drainが含まれる。統合版の即切断は従来にとってより厳しい条件。CPUやWi-Fiの揺らぎを排除した統計的な差ではない。

## 変えたこと・変えていないこと
1. 大きなSSEイベントの改行をXSの配列要素探索ではなく、受信ビュー内だけをネイティブで走査する。
2. 既存16 KiBのネットワーク予算に固定リングを置き、SDKから直接書き込む。消費中の領域は借用終了まで上書きしない。小さな断片が8個に達しただけで読めなくなる旧上限を廃止した。
3. 既存4×2,048バイトのPCM枠へすぐ書けるときだけ、不要な非同期待機を省く。満杯時・取消時は従来どおり待機または停止する。

再生の先行バッファ・開始待ち・再生速度・文節分けは変えていない。統合版では即切断・短長×2速度を2巡し、**8/8で規定PCM量と完了を確認、ソケット終端での未読は0**。終端そのものが失われた入力、満杯による未読までは成功扱いしない。

## まだ言えないこと
短い実時間送信では統合版でも全DMA枠の空き通知が各9回残った。この通知は供給に余裕がない指標であり、聞こえる途切れそのものではない。実サービスのWAN/TLS・データ生成間隔はこのフィクスチャと異なる。本人の会話は自動送信せず、実音の途切れ完全解消とはしていない。
