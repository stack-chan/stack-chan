# Mobile input envelope (preparation only)

The current entry point is `mobile_canary.py --envelope-file <new path>`. It has no USB or network code. It prints a public descriptor, holds a private RSA key only in its process, waits at most ten minutes for a ciphertext-only envelope file, and accepts only the public fixture `mgst_` followed by 43 `A` characters. No genuine credential should be entered during this phase.

A separate owner-authenticated HTTPS relay may store the public descriptor and one ciphertext. The owner-authenticated broker consumes that ciphertext and writes the envelope file on the desktop. Site service credentials and the private key are never transferred between these participants. The relay must enforce owner authentication, bounded bodies, expiry, one atomic receipt/consume, no body logging, and no caching. The browser must clear its input immediately after encryption, prevent double submits, and never put the input in URLs, storage, analytics or error text.

Protocol: descriptor v1, 32-byte random session encoded as 43 unpadded base64url characters, 2048-bit RSA SPKI DER in standard base64, SHA256 SPKI fingerprint as 64 lowercase hex. RSA-OAEP uses SHA256 and MGF1-SHA256; label is ASCII session. Plaintext is ASCII `MUSESDK1\n<session>\n<48-character token>`. Envelope has exactly `v`, `session`, `ciphertext` (standard canonical base64, 256 ciphertext bytes). The receiver uses a monotonic deadline and atomically consumes its key once, including failed decryption. Browser WebCrypto interoperability is tested with Node; that does not prove mobile browser UI operation.

This does not make a malicious frontend harmless. Its script can steal input before encryption or replace keys. The authenticated HTTPS origin and deployed script remain trusted. Use a fixed frontend with no third-party JavaScript and restrictive CSP; present the public-key fingerprint separately for comparison. Do not claim end-to-end security against a compromised frontend.

Python/JavaScript immutable temporary strings and crypto library allocations cannot be guaranteed forensically erased. Mutable buffers are wiped, private-key references are released, and no cleartext is deliberately written to disk or logs. A process exit/timeout abandons the transfer and requires a fresh session.

Actual token input, persistent device saving and later transmission to Muse require the separately promised confirmation of destination and workflow. The canary receiver intentionally has no real-token provisioning mode. Never reinterpret CANARY PASS as device provisioning, authentication or conversation success.

## Prepared device-save adapter

`mobile_save.py` is an import-only adapter, not an enabled receiver or command. The caller must first obtain the separately promised user confirmation, then explicitly pass `approved=True` and the intended serial port and verified USB serial identity. A boolean is not evidence of user authorization; the coordinator owns that gate. The adapter checks VID/PID/serial before decrypting, opens only that port, and sends RAM bytes to the USB provisioner. A CANARY response cannot count as SAVED. Failure is an unknown result, not a guarantee that no device write happened. All mutable buffers are wiped on every exit and the envelope key is closed. Tests use public fixtures and mocks only; no actual token save has been performed.

The current StopWatch build has NVS encryption, flash encryption and secure boot disabled in sdkconfig. The native store uses ordinary `nvs_open`; do not describe its persisted token as encrypted-at-rest. Physical access or firmware access may recover it. No security configuration or eFuse is changed by this workflow. Firmware build flags alone are not a complete eFuse hardware audit.

USB transfers themselves contain plaintext token bytes to the selected physical device. VID/PID/serial matching selects the intended USB device; it is not firmware attestation or cryptographic authentication. The caller must flash and verify the approved provisioning image beforehand. Serial input is cleared before reset, status matching uses complete lines, short writes fail, and mutable chunks are wiped. pyserial, operating-system and USB-driver internal copies remain outside guaranteed zeroization. Saving in unencrypted NVS and later Muse transmission are separate approval gates.

## Dormant operational receiver

`mobile_receiver.py` is prepared but must not be started before the coordinator obtains the separate user approval for the named Site, RAM decryption on NucBox, plaintext USB delivery, and unencrypted device storage. `--approved-save` records that the trusted coordinator has obtained approval; it does not obtain approval by itself. Before launch, coordinate COM18, flash/verify the dedicated SDK provisioning image, and supply the independently checked USB serial identity. The default invocation refuses before key generation. A fresh key and fingerprint are generated for each approved attempt; the old canary fingerprint is never reused.

The only deliberate persistent secret destination is StopWatch NVS `muse_sdk/sdk_token`. The Site relay and broker file contain ciphertext only; browser input and desktop RAM temporarily contain plaintext. The later Muse pairing app receives this SDK token inside the community-v5 encrypted message only under the separately approved pairing workflow. No account refresh/access token should be pasted into this input screen. The current public Site remains canary-only until separately enabled and verified.

The broker must finish writing a ciphertext-only temporary file in the destination directory, then atomically rename it to the expected envelope filename. In-place writes may be observed partially and are rejected; rejection burns the session rather than retrying uncertain data. Relay ciphertext deletion does not establish removal from provider backups. Browser extensions, swap, crash dumps and OS/USB library copies remain outside the application-level wipe guarantee.
