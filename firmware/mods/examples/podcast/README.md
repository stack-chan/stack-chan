# Podcast MOD（M5StackChan CoreS3）

mini app の画面で登録した RSS 2.0 フィードからエピソードを選び、MP3 を再生します。対応するホストファームウェアへの更新が必要です。

## 登録とインストール

1. `config.ts` の `feeds` に番組名と RSS URL を記入します。登録内容は MOD に含まれます。

   ```ts
   export const feeds: { title: string; url: string }[] = [
     { title: 'My Podcast', url: 'https://example.com/podcast/feed.xml' },
   ]
   ```

2. Wi-Fi を設定し、`firmware/` でホストと MOD を書き込みます。

   ```sh
   npm run build:m5stackchan_cores3
   npm run deploy:m5stackchan_cores3
   npm run mod:m5stackchan_cores3 -- mods/examples/podcast/manifest.json
   ```

   ビルドだけを行う場合：

   ```sh
   npm run build:m5stackchan_cores3
   npm run mod:build -- mods/examples/podcast/manifest.json --mode=release
   ```

3. 画面上部の mini app ランチャーから「Podcast」を開きます。
   - 「番組」「エピソード」をタップして一覧から選びます。「前へ」「次へ」でページを切り替え、「戻る」で再生画面に戻ります。
   - ▶／Ⅱ で再生・一時停止・再開、■ で停止します。シークバーをタップまたはドラッグして再生位置を移動できます。RSS の取得に失敗した時だけエピソード欄の隣に「更新」を表示し、取得を再試行できます。通常時・取得中は表示しません。取得中・取得失敗はエピソード欄に、再生状態・再生エラーはシークバーの時刻表示にまとめています。独立したステータス行や取得件数上限の注記は表示しません。
   - 上部バーからアプリを閉じても、再生と顔の音符エフェクト、RSS 取得は続きます。再び開くと現在の再生位置と選択済みのエピソードを表示します。
   - RSS の初回取得は Podcast を初めて開いた時に始まります。以後は閉じても取得・再生を継続します。
   - 起動・番組変更・一覧更新では自動再生しません。ドロワーへの Podcast 操作項目の追加は行いません。

通常の MOD の `onContextCreated` から `context.ui.miniApps.register()` で登録しています。音声・RSS 処理はホストの権限を持つ MOD が担当し、画面の終了時には UI の購読を解除します。再生の寿命は MOD が管理します。隔離された `miniapp` エントリーポイントは使いません。

UI はホストの `context.i18n` と MOD の翻訳リソースを使い、日本語・英語・簡体字中国語に対応します。ホストの「設定 → 言語」で選んだ言語に合わせて、Podcast を開いた時に文言とフォントを選びます。番組名・エピソード名は RSS の原文を表示します。中国語 UI 用フォントはホストと同じ TTF ソースを再利用し、MOD に必要な字形だけをビットマップ化します。任意の中国語タイトルの全字形は収録していません。フォントの出典とライセンスは [ホスト側のフォント説明](../../../host/modules/ui/assets/fonts/StackchanCJK-Regular.README.md)を参照してください。

## 対応範囲

- HTTP/HTTPS の直接 MP3。相対 URL を含む最大 5 回のリダイレクトに対応します。HTTPS から HTTP へのリダイレクトは、RSS・音声・画像のすべてで拒否します。直接指定した HTTP は LAN の試験用サーバーなどに使用でき、証明書検証の対象外です。TLS 証明書検証は有効です。ホストが信頼する CA によっては接続できない配信元があります。フィードやリダイレクト先のホスト名・ネットワーク範囲は制限していないため、信頼する配信元を登録してください。
- MP3 の入力は 44.1 kHz / 48 kHz。ホストの既存デコーダでモノラル 24 kHz に変換します。先頭の ID3v2 タグを読み飛ばします。音量の上限は 0.2 です。
- 有限長の応答は Content-Length または chunked framing が必要です。受信終了後も残りの音声を再生し、出力完了後に終了を表示します。切断や不完全な応答はエラーにし、先頭からの自動再接続は行いません。
- RSS は UTF-8 の RSS 2.0。番組・エピソードタイトル、GUID、MP3 enclosure を取得します。受信上限 256 KiB、表示上限 20 エピソード、取得するテキストフィールド各 8 KiB、深さ 32。受信上限を超えるフィードはエラーにします。全体を受信後、SDK 標準の C 実装 `XML.parse()` にバイト列を直接渡し、要素ツリーから必要な項目を抽出します。通信・解析は最大 30 秒（Worker の応答待ちは最大 35 秒）、ネットワーク無応答は 10 秒で打ち切ります。
- enclosure の `type="audio/mpeg"` を採用します。type が未指定または `application/octet-stream` の場合は `.mp3` URL のみ採用します。GUID がない場合は enclosure URL を識別子にします。
- 発話・tone・音声バッファ再生は Podcast を停止します。発話後の自動再開、再起動後の途中再開、再生履歴、番組検索、AAC/M4A、HLS、Radiko には対応していません。
- 他ターゲットへの展開は未対応です。

## アート表示

エピソード選択時に `itunes:image`（なければ番組の `itunes:image` または RSS `image/url`）を取得して表示します。エピソード画像の取得に失敗した場合は番組画像を試します。画像がない場合や対応外の場合は音符を表示し、音声の操作は継続できます。同じ URL の選択では取得済みの画像を再利用します。

通信 Worker の C 処理が ESP-IDF の HTTPS クライアント（CA バンドルとホスト名による証明書検証を有効化）を使って 16 KiB の共有リングへ JPEG を分割受信し、別の Worker の C 処理が ESP32-S3 ROM の TJpgDec へ順次渡します。TJpgDec の 1/2・1/4・1/8 縮小と、MCU ごとの C 側の縮小を組み合わせ、縦横比を維持した 64×64 の RGB565 サムネイルを生成します。圧縮画像全体や元画像全体の展開バッファは作りません。受信リング 16 KiB、表示画像 8 KiB、デコーダ作業領域 3304 バイト（CoreS3） のほかに、2 つの Worker の XS 用領域合計 512 KiB、スタック合計 24 KiB、TLS 通信などの一時割り当てが必要です。完了後は Worker を解放し、表示画像 8 KiB だけを保持します。

選択変更時は古い画像取得をキャンセルし、通信・デコードの C 処理が資源を解放して返信してから各 Worker を終了します。通信がブロック中の場合はその通信が戻ってからキャンセルが反映されます（接続・読み取りの待ち時間設定は 5 秒）。古い Worker の終了を待って次の取得を開始し、連続選択でネイティブの通信タスクが増え続けることを防ぎます。mini app を閉じても取得・再生を継続し、選択中の画像を保持します。画像の通信と縮小は UI のスレッドで実行しません。

初期対応は baseline JPEG（各辺 4096 px 以下）、受信 2 MiB 以下、取得全体 60 秒以内です。HTTP の `image/jpeg`、`image/jpg`、`application/octet-stream`、`binary/octet-stream`、種類未指定を受け入れ、実データはネイティブデコーダで検証します。PNG・WebP・progressive JPEG は未対応です。ホストの JPEG 連携を追加しているため、MOD と併せてホストも更新してください。

サムネイルのバイト順はホストの描画形式に合わせます（CoreS3 は RGB565BE、Linux の標準構成は RGB565LE）。デコーダから返る形式と画素をそのまま Bitmap に渡し、追加の変換バッファは作りません。

## 一時停止・シーク

- 再生位置は出力ドライバーが消費した PCM から更新します。一時停止では通信と出力を解放し、再開時に保存した位置から取り直します。停止・エピソード変更・発話による割り込みで位置をリセットします。
- 再生時間は MP3 の Xing/Info/VBRI、RSS の `itunes:duration`、Content-Length とビットレートの順に利用します。後二者は「約」と表示し、VBR と判明した場合はビットレートによる推定を取り消します。長さが不明な間はバー操作を無効にします。末尾まで解析した時点で実際のフレーム長に更新します。
- シークは記録したフレーム境界から HTTP Range で取得し、1 秒のプリロール後に指定位置以前の PCM を捨てます。VBR もフレームごとの時間で計算し、バイト比率では位置を決めません。MP3 のエンコーダー遅延・末尾パディングを除くギャップレス再生は未対応です。
- 未取得の遠い位置ではフレームを順に確認する待ち時間が発生します。Range 非対応のサーバーでは先頭から取り直します。チェックポイントは最大 512 件に制限し、長い番組では間隔を広げます。通信エラーは画面に表示します。

## 共通プレイヤー API

```js
await context.audio.media.start({
  url: 'https://example.com/episode.mp3',
  mode: 'finite', // 'live' は従来の再接続動作
  onProgress({ position, duration, estimated, seekable }) {
    // 出力側の秒数。約 250 ms ごとに通知
  },
  onStateChanged(state, reason) {
    // idle / connecting / buffering / playing / stalled / retrying / error / paused / ended
    trace(`${state}: ${reason ?? ''}\n`)
  },
})
context.audio.media.pause()
await context.audio.media.seek(30) // 秒。一時停止中なら移動後も一時停止を保つ
await context.audio.media.resume()
const { position, duration, estimated, seekable } = context.audio.media.progress
context.audio.media.stop()
```

`start()` の完了は再生開始要求の受付を表します。再生完了は `ended` で通知します。`audio.webRadio` は同じプレイヤーを使用するライブ再生用の互換 API です。発話中などは `start()`・`resume()`・`seek()` が `audio busy` で拒否されます。

XML モジュールをホストへ追加しているため、この版への移行ではホストと MOD の両方を更新してください。JPEG のネイティブ連携も必要なため、以前のホストに MOD のみを書き込むことはできません。

## 検証

```sh
npm run test:unit
STACKCHAN_MODULE_TEST_FILTER=media-playback npm run test:moddable
STACKCHAN_MODULE_TEST_FILTER=podcast-ui npm run test:moddable
STACKCHAN_MODULE_TEST_FILTER=podcast-artwork npm run test:moddable
```

XS テストでは HTTP・出力ドライバー・MP3 デコーダを代替し、実際の共有バッファ、デコード制御、ネイティブ PCM リサンプラー、プレイヤー、RSS 取得、画面への状態通知を通します。Piu の画面テストでは選択、ページ移動、再生停止、取得中の操作制限、終了・再表示と 320×196 の表示領域内への配置も確認します。シークの回帰テストは `screen.context` のタッチ開始・移動・終了を通し、ネイティブの `captureTouch` 呼び出しも検証します。実機の MP3 デコードや DMA 出力の代替にはなりません。

実機確認用サーバーは手元の MP3 を指定して起動します（LAN から接続可能な開発環境で使用）。

```sh
node mods/examples/podcast/fixture-server.mjs /absolute/path/episode.mp3
```

表示されたポートを使い `http://<PCのLAN IP>:8080/feed.xml` を登録してください。Content-Length（Range 対応）、chunked（Range 非対応）、相対リダイレクト、途中切断のエピソードが表示されます。44.1/48 kHz、短い音声、大きな ID3 タグ付き音声で、末尾の音が欠けないこと・終了後に再接続しないことを確認します。再生中の停止、一時停止・再開、前後へのシーク、mini app を閉じた後の継続・再表示、連続選択、発話による停止、切断時のエラー、終了後の再選択も確認します。

既存 WebRadio は同じホストに `mods/examples/web_radio/manifest.json` をインストールし、選局・停止・切断後の復旧を確認してください。

### 実機確認（2026-09-29）

M5StackChan CoreS3（ttyACM0）と NPR News Now の MP3 で、RSS 一覧取得、再生位置の進行、mini app 終了後の再生・音符エフェクト維持、再表示、一時停止、120 秒への移動、再開後の位置の進行、停止を確認しました。XS デバッガーから画面の操作を呼び出して確認しています。実際の指によるドラッグ操作と聴感上の音質は別途確認が必要です。

遠い未取得位置への移動では約 40 秒の読み込みが発生しました。また、再取得が一度無応答タイムアウトとなり、シークを再試行して再生できました。ネットワークの遅延・切断時にはエラーを表示し、有限長音声を自動で先頭から再生し直しません。

ドラッグ開始時の再起動は `captureTouch` への `ticks` 引数の欠落による未処理例外（`SyntaxError: xsArg(3): invalid index`）としてシミュレーターと実機で再現しました。タッチイベントから `ticks` を受け取って渡す修正を行っています。修正後は実機でも Piu のタッチ開始・移動・終了を 10 回繰り返し、指定位置の通知と例外が発生しないことを確認しました（この UI 検証ではシーク先の通知を記録関数で受けています）。

### RSS 解析の変更

旧 JavaScript パーサーの 1 文字ずつの解析と、64 バイトごとの待ち時間を廃止し、SDK 標準の XML パーサーへ置き換えました。受信は 4 KiB までを 1 回の処理とし、TLS・受信・XML 解析を専用 Worker で実行します。UI 側へ渡すのは抽出した最大 20 話のみです。Worker は XS 用に 2 MiB、ネイティブスタックに 12 KiB を確保します（通信などのネイティブ割り当ては別）。完了・失敗・停止時には Worker を終了して解放します。RSS の初回取得は mini app を初めて開く時に始まります。

2026-10-01 の M5StackChan CoreS3 デバッグ版の実測では、ugo の RSS 20 話の解析・抽出が 2716〜3882 ms、通信を含む Worker 内の全体処理が 6662〜9312 ms でした（2 回計測）。再取得と並行して UI 側の 20 ms タイマーを 12 秒間計測し、600 回の実行と最大間隔 412 ms を確認しました。ネットワーク条件で取得時間は変動します。

### アートの実測（2026-10-02）

M5StackChan CoreS3 のデバッグ版で ugo の画像（3000×3000、1,140,416 バイト）を連続 2 回取得しました。いずれも 1/8 縮小デコードから 64×64 RGB565 の画像を生成し、HTTP 応答の最後まで読み取りました。

| 項目 | 1 回目 | 2 回目 |
| --- | ---: | ---: |
| 通信 Worker の取得完了 | 9052 ms | 8831 ms |
| Worker 準備から画像生成完了まで | 9497 ms | 9356 ms |
| デコード処理時間（入力待ちを除く経過時間） | 6788 ms | 6760 ms |
| 受信リングの最大使用量 | 16384 bytes | 16384 bytes |
| 取得前との差から求めた一時メモリ使用量の最大観測値 | 636596 bytes | 636344 bytes |
| 内部RAMの空き容量の最小観測値 | 80543 bytes | 71643 bytes |

通信とデコードは同時に実行します。通信 Worker の取得時間にはリングが満杯の間の待ち時間も含まれ、上表の時間を足す値ではありません。メモリはデコード中に 128 MCU ごとに観測した値で、瞬間的な割り当てのすべてを捉える保証はありません。表示後に保持するサムネイルは 8192 バイトです。

同じ試験中の UI 側の 20 ms タイマーは 943 回実行され、最大間隔は 388 ms でした。Worker の準備を含むため、UI の遅延がゼロという意味ではありません。通信条件や音声再生などの同時処理によって時間・メモリは変わります。

従来の JavaScript の HTTPS 取得で試した際は、60 秒時点で 739896 バイトを受信し、同じ量をデコーダが消費していました。通信側で長時間待っていたため、画像取得には C の HTTPS クライアントを使用しています。

デバッグ版では、終了する Worker が SDK の自動サンプリング中に共通ロックを保持したまま削除されることを避けるため、この 2 つの Worker の自動サンプリングを空のコールバックに置き換えています。デバッガーの停止・再開用のタイマーは保持し、時間・メモリはネイティブ処理自身から測定します。

同じホストで Podcast mini app を開いて RSS を取得した後の画像生成は 10226 ms でした。アート欄の描画対象が 64×64・8192 バイトの Bitmap に更新され、描画時の例外がないことを XS デバッガーで確認しました。この回の追加一時メモリの最大観測値は 655964 バイトです。実際の指による操作・聴感上の音質は今回の画像計測の対象外です。

### 描画形式の修正と確認（2026-10-02）

上記の確認は Bitmap の生成までで、出力画素を検証していませんでした。RGB565BE の CoreS3 に RGB565LE の Bitmap を渡すと Poco が描画をスキップするため、画像が表示されない不具合がありました。C のサムネイル出力をホストの描画形式に合わせ、Bitmap にも同じ形式を設定しました。

修正後は RGB565LE と RGB565BE の XS テストで、JPEG デコードから Poco の出力画素までを検証しています。CoreS3 と同じ RGB565BE の Piu テストでは、画像到着時の再描画と mini app 再表示時の画素を確認します。

M5StackChan CoreS3 のデバッグ版で Podcast mini app を開き、ugo の RSS と画像を取得しました。画像は 9229 ms で完成し、Bitmap と画面の形式がともに RGB565BE でした。実機で同じ Artwork の描画を液晶ドライバーへ転送しながら 8192 バイトの出力画素を採取し、PNG に復元して ugo のアートを確認しました。液晶の撮影による確認ではありません。
